# Minecraft on NixOS + HMCL 经验报告

## 1. 结论

这次问题的真正根因，不是单纯的“环境变量没清掉”，而是 **Nix 打包的 HMCL 启动 wrapper 本身会强制注入 `JAVA_TOOL_OPTIONS`**，从而让 Minecraft 客户端加载了被替换的 GLFW 库，最终在启动阶段触发崩溃。

最终通过 **绕过 Nix HMCL 原始 wrapper、自己提供一个干净的 HMCL 启动入口** 解决了问题。

现在已经验证：

- `nix run .#hmcl` 可以正常启动 HMCL
- `nix develop` 后直接运行 `hmcl` 也可以正常启动 HMCL
- Minecraft 已经可以正常启动

---

## 2. 初始现象

日志里最关键的现象有两类：

### 2.1 Minecraft 崩溃

导出日志里出现：

- `Picked up JAVA_TOOL_OPTIONS: -Dorg.lwjgl.glfw.libname=.../libglfw.so`
- `GLFW error collected during initialization: [GLFW 0x10003] Invalid window hint 0x00020010`
- `java.lang.NullPointerException: Initializing game`
- 崩溃栈定位到：
  - `org.lwjgl.glfw.GLFW.glfwSetPreeditCallback`
  - `com.mojang.blaze3d.platform.InputConstants.setupKeyboardCallbacks`

这说明问题发生在 **GLFW / 输入法 preedit 回调初始化** 阶段，而不是普通的 OpenGL 渲染失败。

### 2.2 清理环境变量后问题仍然存在

即使执行：

```bash
env -u JAVA_TOOL_OPTIONS hmcl
```

或者在 shell / devShell 里：

```bash
unset JAVA_TOOL_OPTIONS
```

Minecraft 仍然会显示：

```text
Picked up JAVA_TOOL_OPTIONS: -Dorg.lwjgl.glfw.libname=...
```

这说明问题并不是“当前 shell 留下来的脏环境”这么简单。

---

## 3. 根因分析

### 3.1 真正的注入源头

最终读到 Nix store 中 HMCL 启动脚本：

- `/nix/store/...-hmcl-3.12.2/bin/hmcl`

其中有关键逻辑，会主动构造并导出：

```bash
JAVA_TOOL_OPTIONS='-Dorg.lwjgl.glfw.libname=/nix/store/.../lib/libglfw.so'$JAVA_TOOL_OPTIONS
export JAVA_TOOL_OPTIONS
```

也就是说：

> 不是你 shell 里残留了 `JAVA_TOOL_OPTIONS`，而是 HMCL 包装脚本自己每次启动都重新塞回去。

所以仅靠：

- `unset JAVA_TOOL_OPTIONS`
- `env -u JAVA_TOOL_OPTIONS hmcl`
- `devShell.shellHook = '' unset JAVA_TOOL_OPTIONS ''`

都不够。

### 3.2 绕过原 wrapper 后出现的新问题

当我不再调用原始 `/nix/store/.../bin/hmcl`，改成直接执行 HMCL 的 jar 时，`JAVA_TOOL_OPTIONS` 注入确实消失了。

但很快又暴露出第二个问题：

```text
libXxf86vm.so.1: cannot open shared object file
```

这说明原始 HMCL wrapper 除了错误注入 `JAVA_TOOL_OPTIONS` 之外，还顺带提供了一组运行时图形/音频库路径。

所以正确方案不是“只去掉注入”，而是：

1. 去掉错误的 `JAVA_TOOL_OPTIONS`
2. 保留 HMCL / JavaFX 正常运行所需的动态库路径

## 4. 我修改了什么

修改文件：

- `flake.nix:17-117`

### 4.1 让 flake 默认使用干净 HMCL

现在默认入口不再直接指向 Nix 自带的 `hmcl` wrapper，而是改成我们自己的 wrapper：

- `flake.nix:58-66`
- `flake.nix:78-92`

核心做法：

```nix
hmclClean = pkgs.writeShellApplication {
  name = "hmcl";
  runtimeInputs = [ jdk ];
  text = ''
    unset JAVA_TOOL_OPTIONS
    export LD_LIBRARY_PATH="${hmclLdLibraryPath}''${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
    exec ${jdk}/bin/java -Djdk.gtk.version=3 -jar ${hmclLibDir}/hmcl-terracotta-patch.jar "$@"
  '';
};
```

也就是：

- 不再执行 `${hmcl}/bin/hmcl`
- 直接执行 `${hmcl}/lib/hmcl/hmcl-terracotta-patch.jar`
- 启动前显式 `unset JAVA_TOOL_OPTIONS`
- 手动补回需要的 `LD_LIBRARY_PATH`

### 4.2 补齐 HMCL / JavaFX 运行依赖库

新增了一组运行时库：

- `flake.nix:21-37`

包括：

- `libglvnd`
- `glib`
- `openal-soft`
- `vulkan-loader`
- `libx11`
- `libxxf86vm`
- `libxext`
- `libxcursor`
- `libxrandr`
- `libxtst`
- `libpulseaudio`
- `wayland`
- `alsa-lib`
- `gtk3`

并用：

```nix
pkgs.lib.makeLibraryPath hmclRuntimeLibs
```

生成统一的 `LD_LIBRARY_PATH`。

### 4.3 修正 `LD_LIBRARY_PATH` 空变量问题

在一次测试中出现：

```text
LD_LIBRARY_PATH: unbound variable
```

因此最终改成更稳妥的写法：

```bash
export LD_LIBRARY_PATH="${hmclLdLibraryPath}''${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
```

这样在 `LD_LIBRARY_PATH` 未定义时也不会报错。

### 4.4 让 devShell 也直接可用

`devShell` 里现在直接把干净的 `hmcl` 放进 `packages`：

- `flake.nix:110-116`

因此进入开发环境后可以直接：

```bash
hmcl
```

而不是依赖 alias 或外部 wrapper。

## 5. 测试过程与依据

我遵循了“改前测试 / 改后同类测试”的方式。

### 5.1 改前测试

测试命令：

```bash
nix run .#default -- --help
nix develop . -c hmcl --help
```

改前现象：

- 会出现：

```text
Picked up JAVA_TOOL_OPTIONS: -Dorg.lwjgl.glfw.libname=...
```

说明原始注入仍然存在。

### 5.2 绕过 wrapper 后测试

改成直接跑 jar 后，重新测试：

- `Picked up JAVA_TOOL_OPTIONS` 消失
- 但出现：

```text
libXxf86vm.so.1: cannot open shared object file
```

说明方向正确，但还缺运行时动态库。

### 5.3 补 runtime libs 后测试

继续补 `LD_LIBRARY_PATH` 与库依赖后，再测：

```bash
nix run .#default -- --help
nix develop . -c bash -lc 'type hmcl; which hmcl; hmcl --help'
```

最终结果：

- 不再出现 `Picked up JAVA_TOOL_OPTIONS`
- 不再出现 `libXxf86vm.so.1` 缺失
- HMCL 正常进入 JavaFX / Prism 初始化
- 后续实际反馈：Minecraft 已可以正常启动

这说明修复链路已经闭环。

## 7. 这次排障的经验总结

### 7.1 不要把“环境问题”只理解成当前 shell 变量

很多时候真正的污染源不在 shell，而在 **Nix 包自带 wrapper**。

如果：

- `unset VAR`
- `env -u VAR cmd`

都无效，就要去读实际被执行的 `/nix/store/.../bin/...` 脚本。

### 7.2 绕过 wrapper 时，要同时接管它原来负责的运行时环境

wrapper 往往做两件事：

1. 注入你不想要的东西
2. 同时补齐程序需要的库路径

如果只绕过第 1 点，不补第 2 点，就会从“错误注入”变成“缺库启动失败”。

### 7.3 最有效的测试是“同一命令改前改后对比”

这次最有效的验证命令就是：

```bash
nix run .#default -- --help
nix develop . -c bash -lc 'type hmcl; which hmcl; hmcl --help'
```

因为它们能直接回答三个问题：

- 实际执行的是哪个 `hmcl`
- 有没有再次注入 `JAVA_TOOL_OPTIONS`
- HMCL / JavaFX 是否已能正常初始化

### 7.4 日志里“401 获取用户属性失败”不是主因

日志中虽然有：

```text
Failed to fetch user properties
Status: 401
```

但从崩溃栈和复现路径看，这不是这次崩溃的主因。真正导致游戏启动失败的，是 GLFW 相关初始化链路。

## 8. 后续建议

1. 后续如果更新 nixpkgs / HMCL 包，优先复测：
   - `nix run .#hmcl`
   - Minecraft 实际启动
2. 如果未来 nixpkgs 上游修复了 HMCL wrapper 的错误注入逻辑，可以考虑回退到官方 wrapper
3. 如果还要支持别的启动器（如 PrismLauncher），建议分开保留各自 wrapper，不要混用排障结论
